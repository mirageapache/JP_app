## 2. 手寫判定分析

資料：字「あ」，手指書寫，空白模式，共 14 筆（正確寫法 2 次 6 筆、含錯誤寫法 8 筆）。
當時門檻（基準值）：avgDistance 14、frechet 20、start/endDistance 22、lengthRatio 0.55～1.7、directionMin 0.5；手指再 × 1.3。

### 2.1 正確寫法：全部通過，但部分筆畫接近門檻

| 筆 | 平均距離 | Fréchet | 終點距離 | 長度比 | 佔門檻比例 |
|---|---|---|---|---|---|
| 第 1 次・橫 | 8.4 | 19.7 | 19.7 | 1.72 | Fréchet 76% |
| 第 1 次・豎 | 12.6 | 16.3 | 16.3 | 0.80 | |
| 第 1 次・環 | 5.3 | 7.9 | 4.7 | 0.97 | |
| 第 2 次・橫 | 8.6 | 20.3 | 20.3 | 1.70 | Fréchet 78% |
| **第 2 次・豎** | **17.5** | **25.4** | 25.4 | 0.71 | **平均距離 96%、Fréchet 98%** |
| 第 2 次・環 | 12.6 | 18.0 | 6.4 | 0.77 | |

**原因**：使用者的字比 KanjiVG 範本寫得寬（橫筆長度比約 1.7）、豎筆偏短。目前的 Fréchet 同時包含大小與位置差異，個人書寫習慣就會被當成「形狀不像」。

### 2.2 錯誤寫法：判定種類

| 書寫內容 | 判定 | 正確與否 |
|---|---|---|
| 先寫第 2 筆（豎）×2 | 順序錯誤（第 2 筆） | ✅ |
| 豎與環連成一筆（長度比 3.14） | 順序錯誤（第 3 筆） | ❌ 應判為形狀錯誤／連筆 |
| 環的起筆與繞法錯誤 | 形狀不像 | ✅ |
| 環整個反向書寫 | 方向反了 | ✅ |

**原因**：順序錯誤的比對門檻放寬 1.3 倍，又疊加手指的 1.3 倍（實際 1.69 倍），長度比上限被放到 2.87，連筆也被認成「寫到第 3 筆」。

### 2.3 程式 bug：每筆開頭的座標重複

每一筆開頭都出現 `a, b, c, b, c, …` 的模式（前兩個點被記錄兩次，起點來回折返）。原因是 iOS 在第一次 `pointermove` 時，`getCoalescedEvents()` 會回傳已處理過的點。影響起點方向與長度的計算。

### 2.4 修正方向（P1a 第一項工作）

1. 依事件時間戳去除重複的點
2. 形狀與位置分開判斷：形狀改用**正規化**（平移到同中心、縮放到同長度）後的 Fréchet；位置以較寬鬆的起訖點距離判斷
3. 順序錯誤不再疊加放寬，另一筆的長度比例須在正常範圍；新增**連筆**偵測（使用者筆畫約等於「本筆 + 下一筆」時提示）
4. 這 14 筆存成 `tests/fixtures/strokes/` 的回歸測試資料：正確的必須通過、錯誤的種類必須正確

### 2.5 資料量不足

只有一個字、只有手指。修正後需再收集：

- 有點畫、短筆的字：ぬ、そ、き、ふ、が
- 描摹模式
- Apple Pencil（若有）

## 3. UI 函式庫

兩者實測手感差不多。**決定（2026-10-25）：都不採用，沿用自訂元件；日後導入專案擁有者自行開發的個人 UI 元件庫。** 理由：

- 設計系統元件已在 `src/styles/app.css` 完整實作，與確認過的 UI 範例一致
- Vant 光 CSS 約 200 KB，需以 themeVars 逐項覆寫；Konsta 需要 Tailwind，預設 iOS 藍也需覆寫
- 本 App 需要的元件少（列表、按鈕、開關、分段控制、底部面板），自訂版本已足夠
